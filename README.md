# SyncScribe Backend

SyncScribe помогает держать техническую документацию в актуальном состоянии. Пользователь загружает документ и источники истины: release notes, протоколы встреч, заметки, файлы, ссылки на страницы. Языковая модель сравнивает документ с каждым источником и предлагает точечные правки: что добавить, что изменить, что удалить. Пользователь просматривает правки, при необходимости редактирует их текст, принимает или отклоняет и выгружает итоговый файл в исходном формате.

Сервис рассчитан на технических писателей, инженеров внедрения и пресейла, то есть на тех, кто поддерживает пользовательскую и проектную документацию продукта, который быстро меняется.

Этот репозиторий содержит бэкенд: HTTP API, фоновый воркер анализа, работу с языковой моделью, разбор и сборку документов. Веб-клиент живёт в отдельном репозитории и работает с этим API.

## Как это работает

Весь путь документа от загрузки до выгрузки:

1. **Загрузка.** Пользователь создаёт проект и загружает документ (`.docx`, `.md`, `.txt`). Файл сохраняется в S3-совместимое хранилище, в базе появляется запись документа в статусе `draft`.
2. **Источники.** К проекту или конкретному документу добавляются источники: файл, текстовая заметка или ссылка на страницу. Источники проекта участвуют в анализе всех его документов, источники документа — только его.
3. **Запуск анализа.** API создаёт задачу анализа и ставит её в очередь. Документ переходит в `in_progress`.
4. **Анализ.** Воркер разбирает документ в текст один раз, затем для каждого источника параллельно: получает текст источника, собирает промпт, вызывает модель, проверяет ответ и сохраняет правки.
5. **Итог анализа.** Когда обработаны все источники, задача завершается. Если правки есть, документ переходит в `awaiting_approval`, если нет — сразу в `ready`. Клиент узнаёт о смене статуса через SSE.
6. **Ревью.** Пользователь видит каждую правку с обоснованием от модели и оценкой уверенности. Правку можно принять, отклонить или принять с собственной редакцией текста. Решения сохраняются атомарно, с защитой от одновременного редактирования.
7. **Экспорт.** Когда решения приняты по всем правкам, документ становится `ready`. Принятые правки применяются к исходному файлу, и пользователь скачивает результат в том же формате.

## Работа с языковой моделью

### Без привязки к конкретной модели

Сервис не зависит от конкретной модели или поставщика. Он работает с любым API, совместимым с OpenAI Chat Completions: это общий протокол для локальных движков (Ollama, vLLM, LM Studio, llama.cpp server), облачных сервисов и агрегаторов. Смена модели — это смена переменных окружения, код при этом не меняется.

Всё, чем поставщики отличаются друг от друга, сведено к трём параметрам:

| Параметр | Переменная | Пример |
|---|---|---|
| Адрес API | `LLM_ENDPOINT` | `http://localhost:11434/v1` |
| Имя модели | `LLM_MODEL` | `qwen2.5:14b` |
| Способ авторизации | `LLM_AUTH` + `LLM_API_KEY` | `none`, `bearer` или `oauth_gigachat` |

Остальная логика — промпт, разбор ответа, повторы, проверка правок — общая для всех.

Домен знает только порт `LLMClient` (`app/domain/interfaces/llm_client.py`) с двумя методами:

- `generate_suggestions(document_text, source_text, document_format)` возвращает пакет правок `LLMSuggestionBatch`;
- `health_check()` проверяет, доступна ли модель.

Реализации живут в инфраструктуре (`app/infrastructure/llm/`), выбирает их фабрика по `LLM_PROVIDER`:

- `stub` — заглушка без внешних вызовов: возвращает одну демонстрационную правку. Подходит для локальной разработки интерфейса и тестов.
- `openai_compatible` — универсальный клиент `OpenAICompatibleClient`. Значения `remote_http` и `onprem` принимаются как синонимы для старых конфигураций.

### Подключение модели

Готовые примеры есть в `.env.example`.

Локальная модель без ключа (Ollama, vLLM, LM Studio):

```env
LLM_PROVIDER=openai_compatible
LLM_ENDPOINT=http://host.docker.internal:11434/v1
LLM_MODEL=qwen2.5:14b
LLM_AUTH=none
```

Облачный сервис или агрегатор с API-ключом:

```env
LLM_PROVIDER=openai_compatible
LLM_ENDPOINT=https://openrouter.ai/api/v1
LLM_MODEL=openai/gpt-4o-mini
LLM_AUTH=bearer
LLM_API_KEY=sk-...
```

Сервис, который выдаёт короткоживущий токен в обмен на постоянный ключ авторизации (так устроен, например, GigaChat):

```env
LLM_PROVIDER=openai_compatible
LLM_ENDPOINT=https://gigachat.devices.sberbank.ru/api/v1
LLM_MODEL=GigaChat
LLM_AUTH=oauth_gigachat
LLM_API_KEY=<ключ авторизации>
LLM_OAUTH_URL=https://ngw.devices.sberbank.ru:9443/api/v2/oauth
LLM_OAUTH_SCOPE=GIGACHAT_API_PERS
LLM_CA_BUNDLE=/srv/app/certs/russian_trusted_root_ca.pem
```

Если API использует собственный корневой сертификат, положите PEM в папку `certs/` репозитория: compose монтирует её в контейнеры API и воркера как `/srv/app/certs` (только чтение), путь к файлу указывается в `LLM_CA_BUNDLE`.

Проверить подключение можно запросом `GET /api/v1/system/llm-health` (только для роли `admin`): он вызывает `GET {LLM_ENDPOINT}/models` и тем самым проверяет и адрес, и авторизацию.

### Подключение ML-конвейера (контракт 2.0)

Конвейер анализирует документ целиком со всеми источниками за один запрос: документ уходит блоками (`block_id`, тип, текст, признак `editable`), источники — текстом в едином формате (заголовки `#`, пункты `- `, строки таблиц `| … |`). Порт — `DocumentAnalyzer` (`app/domain/interfaces/document_analyzer.py`), JSON контракта — только в `app/infrastructure/ml_pipeline/schemas.py`. Пример запроса и ответов — `tests/fixtures/ml_contract/`.

Способ подключения выбирается `ANALYSIS_PROVIDER`:

- `legacy_llm` — по умолчанию: прежний анализ «документ × источник» через `LLM_*`;
- `ml_plugin` — конвейер установлен Python-пакетом в образ воркера; `ML_PLUGIN_ENTRYPOINT=package.module:function` — функция «dict запроса → dict ответа». Функция импортируется при старте воркера и вызывается в отдельном потоке с дедлайном `ML_WAIT_SECONDS`;
- `ml_http` — конвейер как сервис: `POST {ML_ENDPOINT}` с JSON запроса. Ответ — сразу `200` с ответом контракта или `202 {request_id}` и опрос `GET {ML_ENDPOINT}/{request_id}` каждые `ML_POLL_SECONDS`, пока статус `queued`/`running`. Сетевые сбои, `429` и `5xx` повторяются (`ML_MAX_RETRIES`), `4xx` — нет. Ключ `ML_API_KEY` передаётся как `Bearer`;
- `stub` — заглушка с правками по реальным блокам документа, для разработки интерфейса.

```env
ANALYSIS_PROVIDER=ml_http
ML_ENDPOINT=http://ml:8000/v1/analyze
ML_HEALTH_URL=http://ml:8000/health
ML_HTTP_MODE=sync
ML_API_KEY=<общий ключ>
```

Этот пример подключает конвейер [syncscribe-ml](https://github.com/rishotkaB/syncscribe-ml) из сервиса `ml` в `docker-compose.yml`. Сервис поднимается только с профилем: `docker compose --profile ml up`. Образ собирается в их репозитории (`docker build -t syncscribe-ml .`); имя образа задаёт `ML_IMAGE`. Ключ `ML_API_KEY` сервис получает как `SYNCSCRIBE_ML_API_KEY`, число слотов — из `ANALYSIS_V2_CONCURRENCY`. LLM конвейера настраивается переменными `ML_LLM_PROVIDER`, `ML_LLM_MODEL`, `ML_OLLAMA_HOST`, `ML_LLM_BASE_URL`, `ML_LLM_API_KEY` и `ML_EMBED_BACKEND`. Наши `LLM_*` в контейнер не передаются: у конвейера переменные с теми же именами, но другим смыслом.

Проверить подключение можно запросом `GET /api/v1/system/analysis-health` (только для роли `admin`). Ответ `{status, provider, contract_version, healthy, queue: {name, consumers}}`. `healthy` — ответ `ML_HEALTH_URL` (при `legacy_llm` — проверка `LLM_*`), а `null` — проверить нечем: адрес не задан или `ml_plugin`, который установлен только в образе воркера. `queue.consumers` — сколько воркеров слушают очередь анализа, `null` — брокер не ответил. `status` равен `down`, если конвейер недоступен или очередь никто не слушает, и `unknown`, если что-то проверить не удалось. Прежний `GET /system/llm-health` оставлен без изменений и помечен устаревшим. `GET /system/capabilities` отдаёт `analysis.contract_version`: `"2.0"` для анализа по контракту и `null` для `legacy_llm`.

Каждый вызов конвейера пишет в лог одну запись «Анализ v2: вызов конвейера». В ней `job_id`, `request_id` (по нему запись сопоставляется с логами конвейера), `attempt`, `provider`, `outcome` (`completed`, `failed`, `timeout`, `invalid_response`) и `duration_ms`. Там же счётчики: `blocks`, `sources`, `suggestions`, `flags`, `checked_blocks`, `failed_blocks`. Отброшенные правки логируются отдельно, по причинам и итогом `dropped_total`. Тексты документа и правок в логи не попадают.

`ML_WAIT_SECONDS` должен быть меньше `ANALYSIS_TASK_TIME_LIMIT_SECONDS`: запас нужен на загрузку источников и запись результата. Лимиты запроса `ANALYSIS_MAX_*` проверяются до вызова конвейера; превышение — ошибка `LLM_INPUT_TOO_LARGE`.

При `ANALYSIS_PROVIDER` ≠ `legacy_llm` анализ выполняет одна задача Celery `analyze_document_for_job` на документ: все источники уходят в один запрос, правки и статус записываются одной транзакцией. Повторная доставка задачи или отмена во время ожидания конвейера не создают лишних правок. Таймаут и временный сбой конвейера повторяются до `ANALYSIS_RETRY_LIMIT` раз (не больше 6) с паузой 30·2ⁿ с; `ANALYSIS_TASK_TIME_LIMIT_SECONDS` — не больше 3000, чтобы задача укладывалась в visibility timeout брокера Redis. Недоступный источник делает результат частичным (`partial_success`), недоступность всех — ошибкой `SOURCES_UNAVAILABLE`. При `ANALYSIS_STORE_PAYLOADS=true` запрос и разобранный ответ сохраняются в хранилище по ключам `analysis_runs/{job_id}/{attempt}.request.json` и `….response.json`.

Задача v2 идёт в отдельную очередь Celery `ANALYSIS_V2_QUEUE` (по умолчанию `analysis_v2`), её слушает сервис `worker-analysis` с `ANALYSIS_V2_CONCURRENCY` процессами (по умолчанию 1). Остальные задачи остаются в общей очереди `celery` у сервиса `worker`. Конвейер выдерживает ограниченное число одновременных прогонов: если отправить больше, лишние получат `429` и после повторов упадут с `LLM_UNAVAILABLE`. Поэтому `ANALYSIS_V2_CONCURRENCY` (в сумме по всем репликам `worker-analysis`) держите не больше числа слотов конвейера; остальные документы ждут в очереди брокера в статусе `dispatched`, лимиты задачи на это ожидание не распространяются. `worker-analysis` поднимается вместе с остальными сервисами при `docker compose up`. При обновлении с версии без него выполните `docker compose up -d --build`: compose создаст новый сервис и перезапустит `worker` с `-Q celery`. Задачи v2, поставленные до обновления в очередь `celery`, выполнит `worker`. Если `worker-analysis` остановлен, задачи v2 не начнутся, а `GET /system/analysis-health` покажет `down` и `consumers: 0`.

Каждая правка v2 привязана к блоку документа: `block_id` — ref блока из `GET /editor` (`content.blocks`), `start_offset`/`end_offset` — границы `original_text` в `content.plain_text` в символах Unicode. Правки выдаются в порядке ответа конвейера (`position`). В задаче анализа сохраняются `request_id` запроса к конвейеру и сводка его `meta`; `checked_blocks` и `failed_blocks` отдаются в `GET …/{d}/analysis-jobs/{j}`.

Если фраза повторяется, конвейер возвращает правку на каждое место. Несколько правок с одним `original_text` в одном блоке получают вхождения по порядку ответа; правка сверх числа вхождений отбрасывается. Правки, которые меняют одну фразу одинаково (без учёта регистра, пробелов и «ё/е»), получают общий `group_key`: `GET …/suggestions?group_key=…` отдаёт всю группу, а `suggestion_groups` в `GET /editor` — размер каждой группы и число нерешённых. Группа — подсказка для массового решения через `PATCH /suggestions`, каждая правка решается отдельно. При `SUGGESTION_PROPAGATE_EXACT=true` (по умолчанию выключено) остальные точные повторы исправленной фразы в редактируемых блоках получают такую же правку с `origin = propagated` и пометкой «Найдено автоматически»; лимиты — `SUGGESTION_PROPAGATE_MAX_GROUPS` и `SUGGESTION_PROPAGATE_MAX_PER_GROUP`.

Флаги «проверьте вручную» (`flags` в ответе конвейера) сохраняются в `analysis_flags` той же транзакцией, что и правки. Флаг — место документа, которое человек должен сверить с цитатами источников: правки нет, поэтому флаг не участвует в review-цикле и экспорте и не держит документ в `awaiting_approval` (документ только с флагами сразу становится `ready`). `GET /editor` отдаёт все флаги текущего анализа в `flags` (в порядке ответа конвейера, с `block_id` для подсветки и `quotes[{source_name, text}]`) и число неотмеченных в `counters.flags_pending`; тот же список — `GET …/documents/{d}/flags`. `PATCH …/documents/{d}/flags/{f}` с `{"status": "reviewed" | "pending"}` ставит или снимает отметку и пишет в аудит `flag_review` / `flag_reopen` (повтор того же статуса события не пишет); флаг прежнего анализа — `404`, документ без результатов анализа — `409`. «Сбросить все изменения» (`POST …/editor/reset`) снимает и отметки флагов (`flags_reset_count`). Флагов на анализ сохраняется не больше `ANALYSIS_MAX_FLAGS` (по умолчанию 500); остальные и флаги на несуществующий блок отбрасываются с предупреждением в логе.

Перед вызовом конвейера воркер сохраняет снимок каждого источника: ровно тот текст, который ушёл в запрос (`source_snapshots`, строки задачи в `analysis_job_source_snapshots`). Текст снимка отдаёт `GET /api/v1/projects/{project_id}/source-snapshots/{snapshot_id}/content`.

Основания правок. Цитаты источников воркер берёт из структурного поля `quotes` правки, если конвейер его вернул, иначе из конца строки `rationale` в форматах harness («Источник: «…» (имя)», «Источник (имя): «…»»). Каждая цитата ищется в снимке своего источника: дословно, затем после свёртки кавычек, тире, пробелов, регистра и разметки, затем по сегменту с наибольшей долей слов цитаты (порог `ANALYSIS_EVIDENCE_MIN_CONTAINMENT`, по умолчанию 0.6, гипотеза). Результат хранится в `suggestions.evidence` и приходит в `SuggestionResponse.evidence`: `match` (`exact`, `approximate`, `not_found`), диапазон в тексте снимка, `snapshot_id`, номер сегмента, `locator` (для DOCX диапазон порядковых номеров непустых абзацев файла) и `original_file_available` (файл источника тот же, что разбирался при анализе). Правка ссылается только на источники с найденными цитатами; если не нашлась ни одна, у неё все источники запроса. Цитаты флагов получают те же поля. Счётчики `evidence_exact`, `evidence_approximate`, `evidence_not_found`, `evidence_unparsed` пишутся в `pipeline_meta.evidence` задачи и в лог «Анализ v2: основания правок»; рост `evidence_unparsed` означает, что формат обоснования в harness изменился.

Повторный анализ без изменений. После загрузки источников воркер считает хэш входа: sha256 от версии контракта, провайдера, байтов файла документа и отсортированных пар (имя источника, хэш снимка). Хэш хранится в `analysis_jobs.input_hash`. Если он совпал с последней полной задачей того же документа (`success`, без `partial_success` и упавших блоков), конвейер не вызывается: правки, флаги и связи правок с источниками копируются в новую задачу вместе со статусами и решениями пользователя, `carried_from_id` указывает на исходную строку. Перенос выключен, если хотя бы один источник не загрузился. Режим задаёт `ANALYSIS_INCREMENTAL_MODE`: `off` всегда вызывает ML, `reuse` переносит результат, `delta` (по умолчанию) делает то же и для полных прогонов считает долю символов источников в новых сегментах относительно прошлой задачи. Запуск с `{"strategy": "full"}` в `POST /analysis-jobs` и `POST /analysis-jobs/bulk` всегда вызывает ML: хэш не видит изменений разбора, эвристик и модели внутри harness. В ответе задачи `incremental` (`mode` `reused`, `delta` или `full`, `reason`, `baseline_job_id`, `changed_share`, `segments_added`, `segments_removed`) и `run_stats` (`segments_total`, `segments_sent`, `chars_total`, `chars_sent`, `blocks_total`, `blocks_checked` и счётчики harness `quick`, `full`, `conflict`, `add_checks`, `llm_seconds`, если конвейер их вернул). Те же поля лежат в `pipeline_meta`. При переносе в лог пишется «Анализ v2: перенесён результат прошлой задачи», а записи «Анализ v2: вызов конвейера» нет.

Выборочная проверка (`ANALYSIS_INCREMENTAL_MODE=delta`). Если хэш входа изменился, но файл документа, версия контракта и провайдер те же, что у прошлой полной задачи, воркер проверяет заново только затронутые блоки. Конвейер получает документ целиком как контекст, редактируемыми в запросе остаются выбранные блоки, а каждый источник урезан до новых сегментов с `ANALYSIS_DELTA_CONTEXT_SEGMENTS` соседями с каждой стороны, заголовком их раздела и до `ANALYSIS_DELTA_SUPPORT_SEGMENTS` неизменённых сегментов, ближе всего похожих по словам. Блок выбирается, если он входит в `ANALYSIS_DELTA_BLOCKS_PER_SEGMENT` лучших по BM25 для нового сегмента с оценкой не ниже `ANALYSIS_DELTA_SCORE_THRESHOLD`, если с сегментом его связывает редкий токен с цифрой (число, версия, код), который встречается не больше чем в `ANALYSIS_DELTA_RARE_BLOCKS` блоках, если основание его прошлой правки или флага изменилось или если на нём стоит флаг прошлой задачи. Слова сравниваются по первым `ANALYSIS_DELTA_STEM_CHARS` символам, чтобы падежные формы совпадали.

Результат собирается из прошлой задачи и нового ответа. Правки и флаги невыбранных блоков переносятся с решениями пользователя. У выбранного блока ожидающие правки заменяются новым ответом, а принятые и отклонённые сохраняются; новая правка, совпавшая с прошлой по блоку, типу и тексту, получает прошлое решение и не показывается повторно. Если цитата перенесённой принятой или отклонённой правки исчезла из источника, у правки ставится `stale` (`SuggestionResponse.stale`), а на блок добавляется флаг `evidence_removed`. Добавление, которое опирается только на неизменённые сегменты источника, отбрасывается: такое предложение уже было в полной задаче. Задача хранит `baseline_job_id` прошлой задачи, а в `incremental` пишутся `chain_length`, `blocks_selected`, `selected_by_*`, `carried_suggestions`, `carried_flags`, `stale`, `replaced`, `inherited`, `dropped_add` и `evidence_flags`.

Вход проверяется полным анализом, и `incremental.fallback_reason` объясняет почему, если: изменился файл документа (`document_changed`), версия контракта (`contract_changed`) или провайдер (`provider_changed`); подряд прошло `ANALYSIS_DELTA_MAX_CHAIN` выборочных задач (`chain_limit`); доля символов в новых сегментах больше `ANALYSIS_DELTA_MAX_CHANGED_SHARE` (`changed_share`); выбрано больше `ANALYSIS_DELTA_MAX_BLOCKS_SHARE` проверяемых блоков (`blocks_share`); сегменты добавлены, а ни один блок не выбран (`no_blocks_matched`); у прошлой задачи нет отпечатков сегментов (`fingerprints_unavailable`). Если изменились только удалённые сегменты и основания, конвейер не вызывается: результат собирается переносом с отметками `stale`.

С вероятностью `ANALYSIS_DELTA_AUDIT_RATE` (по умолчанию 0) после выборочной задачи тот же вход проверяется полным анализом, и в `incremental.audit` пишутся `blocks_full`, `blocks_delta`, `missed`, `extra` и `recall` по блокам с правками или флагами. Контрольный прогон выполняется в той же задаче и удлиняет её. Все пороги `ANALYSIS_DELTA_*` подобраны на синтетических примерах и являются гипотезами: полнота выборочной проверки на реальной модели не измерена. Известное ограничение: пересказ изменения без общих с блоком слов и чисел не выбирает этот блок, такое расхождение найдёт следующий полный анализ.

### Авторизация

Авторизация отделена от транспорта (`app/infrastructure/llm/auth.py`). Новый способ авторизации добавляется как новая стратегия, а не как новый клиент.

- `none` — без заголовка `Authorization`, для локальных движков.
- `bearer` — `Authorization: Bearer <LLM_API_KEY>`.
- `oauth_gigachat` — постоянный ключ (Basic) обменивается на access-токен запросом на `LLM_OAUTH_URL` с уникальным `RqUID` и `scope`. Токен кэшируется в памяти процесса и в Redis, чтобы процессы воркера не запрашивали каждый свой токен: при одновременном старте нескольких источников OAuth-сервер ответил бы на такую пачку ошибкой 429. Токен обновляется за 60 секунд до истечения; если сервер не сообщил срок, токен считается живущим 25 минут. Если модель ответила 401, токен обновляется и запрос повторяется ровно один раз.

### Надёжность вызова

- **Повторы временных сбоев.** Обрыв соединения, таймаут, ответы 429 и 5xx повторяются до `LLM_MAX_RETRIES` раз с задержкой 1, 2, 4… секунды (не больше 30 секунд). Заголовок `Retry-After` важнее расчётной задержки. Остальные ответы 4xx не повторяются: это ошибка запроса, повтор её не исправит. Запрос токена авторизации повторяется по тем же правилам.
- **Повторы на уровне задачи.** Если модель недоступна и после повторов клиента, воркер откладывает обработку источника и пробует ещё до трёх раз с растущей паузой, после чего источник считается неуспешным.
- **Таймауты.** Каждый запрос ограничен `LLM_TIMEOUT_SECONDS`; обработка одного источника ограничена 9 минутами (мягкий лимит) и 9,5 минутами (жёсткий).
- **Размер входа.** Если документ и источник вместе длиннее `LLM_MAX_INPUT_CHARS` символов, источник завершается ошибкой `LLM_INPUT_TOO_LARGE`. Текст сознательно не обрезается: правки по урезанному документу были бы неверными.
- **Температура** по умолчанию 0.1: от модели нужна точность копирования фрагментов, а не разнообразие формулировок.

### Промпт

Промпт собирается в `app/infrastructure/llm/prompt.py` и отправляется одним сообщением пользователя. В нём три части: инструкция, формат документа и данные.

Документ и источник приходят от пользователя и могут содержать текст, похожий на команды модели. Поэтому данные отделены от инструкции:

- документ обёрнут в тег `<document>`, источник — в `<source>`;
- совпадения с этими тегами внутри текста экранируются, чтобы данные не могли «закрыть» тег и продолжиться как инструкция;
- инструкция прямо запрещает выполнять указания из данных.

Это снижает риск prompt injection, но не исключает его полностью. Поэтому ответ модели всегда проходит проверку схемы, проверку якорей и ручное ревью пользователем.

Инструкция задаёт модели следующие правила:

- каждое расхождение с источником — отдельная правка;
- `section_ref` — дословный заголовок раздела документа, а не источника;
- фрагменты документа (`old_text`, `insert_after`) копируются дословно и в пределах одного абзаца; если меняется одно предложение, указывается предложение, а не весь абзац;
- `new_text` пишется в стиле и терминах документа, без служебных сведений источника (дат встреч, номеров решений, пометок вроде «Что менять в документации»);
- замена одного утверждения другим — одна правка `modify`, а не пара `delete` + `add`;
- добавление указывает дословное предложение документа, после которого вставляется новый текст.

В инструкцию включён пример ответа: компактные модели лучше воспроизводят форму примера, чем следуют оговоркам в тексте.

### Формат ответа

Модель должна вернуть JSON такого вида:

```json
{
  "suggestions": [
    {
      "section_ref": "Сроки",
      "change_type": "modify",
      "old_text": "Срок ответа — 10 дней.",
      "new_text": "Срок ответа — 5 дней.",
      "insert_after": "",
      "rationale": "Источник: срок сокращён.",
      "confidence_score": 0.95
    }
  ]
}
```

| Поле | Смысл |
|---|---|
| `section_ref` | Заголовок раздела документа, к которому относится правка |
| `change_type` | `add`, `modify` или `delete` |
| `old_text` | Для `modify` и `delete` — заменяемый или удаляемый фрагмент документа |
| `new_text` | Для `add` и `modify` — новый текст |
| `insert_after` | Для `add` — фрагмент документа, после которого вставить `new_text` (якорь) |
| `rationale` | Почему нужна правка, со ссылкой на источник |
| `confidence_score` | Уверенность модели от 0 до 1 |

Модели часто оборачивают JSON в markdown-ограждения или добавляют пояснения вокруг. Клиент берёт текст из `choices[0].message.content`, вырезает объект от первой `{` до последней `}` и только затем проверяет его схемой (`app/infrastructure/llm/schemas.py`). Ответ без JSON или с неверной структурой даёт ошибку `LLM_INVALID_RESPONSE` для этого источника. Оценка уверенности вне диапазона 0..1 не ломает ответ, а просто отбрасывается.

### Как добавить поставщика

Для любого OpenAI-совместимого API достаточно переменных окружения. Если у поставщика нестандартная авторизация, добавьте стратегию в `auth.py` и значение в `LLM_AUTH`. Если протокол совсем другой, реализуйте порт `LLMClient` и зарегистрируйте его в `app/infrastructure/llm/factory.py`; домен, воркер и API при этом не меняются.

## Работа с текстом и правками

### Разбор документов

Документ разбирается в плоский текст и список разделов (`app/infrastructure/parsers/`). Парсер выбирается по расширению файла.

| Формат | Как читается | Разделы |
|---|---|---|
| `.docx` | Абзацы основного текста через python-docx, по одному на строку | Абзацы со стилем `Heading*` |
| `.md`, `.markdown` | Текст как есть | Строки с `#` … `######` |
| `.txt` | Текст как есть (UTF-8) | Нет |
| `.pdf` | Строки текстового слоя, собранные в блоки (см. «PDF-документы и источники») | По кеглю строки |

Документ с другим расширением, в том числе `.doc`, не принимается: загрузка отвечает 415 (`.doc` нужно сохранить как `.docx`). Файл-источник принимается с расширениями `.docx`, `.htm`, `.html`, `.md`, `.markdown`, `.pdf`, `.txt`; остальные получают 415 до записи в хранилище. Список отдаёт `GET /api/v1/system/capabilities` в `upload.source_extensions`, форма загрузки берёт его оттуда.

### PDF-документы и источники

PDF читается через PDFium (`app/infrastructure/parsers/pdf_*.py`) постранично: страница открывается, из неё берутся символы с координатами, и она закрывается, поэтому память растёт с объёмом текста, а не с размером файла. Строки собираются по координатам, а не по порядку символов в потоке: LibreOffice и другие генераторы пишут цифры и знаки препинания не на своих местах. Дальше строки складываются в блоки: заголовок (кегль от 1,15 основного, короткая строка), абзац (разрыв больше 1,3 межстрочного интервала), пункт списка (маркер или номер), таблица (не меньше двух колонок с совпадающими границами, продолжение на следующей странице остаётся той же таблицей). Строки, которые повторяются на краю больше чем половины страниц, считаются колонтитулами и отбрасываются. Пороги заданы константами в `pdf_blocks.py` и подобраны на тестовом наборе, это гипотеза.

Загрузка проверяет PDF до записи в хранилище: файл с паролем, без текстового слоя (скан без OCR) или длиннее `PDF_MAX_PAGES` страниц (по умолчанию 500) получает 422 с причиной и советом загрузить исходный DOCX. Если текст есть не на всех страницах, источник принимается, а номера пустых страниц приходят в `pages_without_text` ответа загрузки. Для каждого фрагмента источника сохраняются прямоугольники строк на страницах (`locator.kind = "pdf_rects"`, координаты в пространстве страницы PDF без учёта CropBox и поворота), по ним подсвечиваются основания правок. Замеры и непроверенные случаи описаны в `docs/pdf-spike.md`.

PDF-документ проходит ту же проверку при загрузке, а `pages_without_text` приходит в ответе `POST …/documents`. Разбор PDF долгий, поэтому он кэшируется в хранилище рядом с файлом (`<storage_key>.layout`, gzip JSON): внутри записаны версия эвристик и sha256 файла, при расхождении разбор повторяется и кэш перезаписывается. Редактор и воркер читают один кэш, удаление документа или проекта удаляет и его. `GET …/editor` отдаёт у PDF `content.pages` с размерами страниц в точках (с CropBox и поворотом). Воркер после анализа находит каждую правку и флаг на страницах и пишет `geometry = {"rects": [[page, x0, y0, x1, y1], …]}` в тех же координатах, что `pdf_rects`; у вставки берётся символ перед точкой вставки. Сбой поиска геометрии пишется в лог и не роняет анализ, legacy-путь v1 геометрию не считает. По этой геометрии экспорт ставит аннотации рецензирования (раздел «Применение правок и экспорт»).

В `.docx` читаются только абзацы основного текста: таблицы, колонтитулы и сноски в анализ не попадают.

### Нормализация текста

Модель, копируя фрагмент документа, заменяет неразрывные и узкие пробелы обычными, а разложенные Unicode-символы — составными. Чтобы фрагмент из ответа совпадал с документом дословно, текст нормализуется одинаково на входе и на выходе (`app/domain/text_normalization.py`):

- Unicode NFC;
- `\r\n` → `\n`;
- неразрывный, узкий неразрывный, цифровой и тонкий пробелы → обычный пробел;
- пробел нулевой ширины и BOM удаляются.

Парсеры нормализуют текст один раз при разборе, экспортёры нормализуют исходный файл и фрагменты правок перед сравнением.

### Источники

- **Файл** — скачивается из хранилища и разбирается тем же парсером, что и документ.
- **Заметка** — сохраняется как `.txt` и дальше обрабатывается как файл.
- **Ссылка** — страница скачивается воркером в момент анализа. Разрешены только http и https; имя хоста разрешается в адреса, и каждый адрес проходит политику ссылок. Запрос уходит на проверенный IP с исходными Host и SNI (защита от DNS rebinding). Каждый редирект проверяется заново, не больше пяти. Ответ читается потоком и обрывается после `SOURCE_URL_MAX_BYTES` (5 МБ). Тип содержимого выбирает разбор: HTML, Markdown, простой текст и DOCX идут теми же парсерами, что и файлы, неизвестный тип отклоняется. Кодировка определяется по BOM, заголовку Content-Type (если байты им декодируются), `<meta charset>`, строгому UTF-8 и запасной `SOURCE_HTML_FALLBACK_ENCODING`. Из HTML берётся основное содержимое (см. [Текст страницы](#текст-страницы)). Ответ 401 или 403 и форма входа после редиректа на другой хост дают отказ с просьбой сохранить страницу как файл.

#### Внутренние порталы

По умолчанию ссылка принимается, только если хост разрешается в публичные адреса. Для порталов закрытого контура задаются `SOURCE_URL_ALLOWED_HOSTS` (точные имена или суффиксы с ведущей точкой, через запятую) и `SOURCE_URL_ALLOWED_NETWORKS` (CIDR через запятую). Внутренний адрес принимается при двух условиях сразу: имя есть в списке и адрес входит в одну из сетей. Loopback, link-local (включая 169.254.169.254), multicast и неопределённые адреса отклоняются при любой настройке. `SOURCE_URL_ALLOW_PUBLIC=false` оставляет только белый список, это режим контура без выхода в интернет.

Подсеть Docker (сеть `syncscribe-net`; Docker по умолчанию выдаёт адреса из 172.16.0.0/12 и 192.168.0.0/16, фактическую подсеть показывает `docker network inspect`) в `SOURCE_URL_ALLOWED_NETWORKS` вносить нельзя: тогда ссылка на имя из списка, разрешённое в адрес контейнера, дотянулась бы до сервисов compose. Имена сервисов (`ml`, `postgres`, `redis`, `seaweedfs`, `backend`) в список хостов тоже не вносятся.

Свой удостоверяющий центр подключается через `SOURCE_URL_CA_BUNDLE`, файл лежит в каталоге `./certs`, который смонтирован в backend и worker. Проверка сертификата остаётся включённой. Сервисный токен портала задаётся JSON-файлом `SOURCE_URL_AUTH_HEADERS_FILE` вида `{"wiki.corp": {"Authorization": "Bearer …"}}`, лучше секретом compose. Заголовки уходят только на свой хост и снимаются при редиректе на другой. Вход через Kerberos и интерактивный SSO не поддерживается; такие страницы сохраняются из браузера и загружаются файлом.

#### Текст страницы

Корень содержимого выбирается по селектору хоста из `SOURCE_HTML_CONTENT_SELECTORS` (JSON, например `{"wiki.corp": "#main-content"}`; ключ с ведущей точкой подходит для поддоменов), затем по единственному `<main>` или `role="main"`, затем по единственному `<article>`, иначе берётся `<body>`. Внутри корня пропускаются nav, aside, form, button, dialog, шапка и подвал вне article и section, скрытые элементы и роли navigation, banner, contentinfo, complementary, search. Если после фильтра осталось меньше `SOURCE_HTML_MIN_KEPT_SHARE` текста страницы (0.1), разбирается весь `<body>`. Страница короче `SOURCE_HTML_MIN_CHARS` (200) со скриптами считается приложением на JavaScript и отклоняется с просьбой сохранить её как файл. Сохранённые из браузера `.html` и `.htm` загружаются как файловые источники и разбираются так же.

`SOURCE_URL_ROBOTS`: `log` пишет запрет `robots.txt` в лог, `enforce` прерывает загрузку, `off` не запрашивает `robots.txt` вовсе. Проверить ссылку сразу после добавления можно через `POST /sources/{s}/check`: ручка загружает и разбирает источник и возвращает `{ok, chars, error}`, ничего не сохраняя.

Посмотреть текст источника без редактирования можно через `GET /sources/{s}/content`; для ссылок и неподдерживаемых файлов ответ сообщает, что предпросмотр недоступен.

### От ответа модели к правке

Ответ модели не сохраняется как есть. Маппер (`app/workers/pipeline/suggestion_mapper.py`) приводит его к виду, который можно применить к документу:

- `modify` с пустым `new_text` становится `delete` — модели часто оформляют удаление именно так;
- `modify`, где `new_text` начинается с `old_text`, становится `add`: модель дописала предложение, повторив абзац. Якорем становится последний абзац `old_text`, в `new_text` остаётся только дописанная часть;
- якорь добавления берётся из `insert_after`, затем из `old_text`. Если якоря нет, а раздел `section_ref` найден в документе, якорем становится первый абзац раздела, и в обоснование добавляется пометка «Место вставки выбрано автоматически…» — пользователь видит, что место выбрала не модель;
- `modify` и `delete` сохраняются только с непустым `old_text`, который дословно присутствует в тексте документа: иначе экспорт не сможет применить правку.

Правка отбрасывается, если:

- у неё неизвестный тип;
- это добавление без якоря;
- якоря добавления нет в тексте документа;
- у `modify` или `delete` отсутствует `old_text` либо этот фрагмент не найден в документе;
- для `.docx` фрагмент `old_text` охватывает несколько абзацев (экспорт ищет фрагмент внутри одного абзаца и всё равно его не применит).

Одна плохая правка не роняет обработку источника: она пропускается, остальные сохраняются. В warning-лог попадают агрегированные причины (`old_text_missing`, `old_text_not_in_document` и другие), `analysis_job_id`, `document_id` и счётчики — без текста документа и ответа модели. Каждая сохранённая правка связывается с источником, на основании которого она создана; API возвращает краткие сведения в поле `sources`, чтобы клиент мог показать название и открыть предпросмотр источника.

### Как хранится правка

| Тип | `original_text` | `suggested_text` |
|---|---|---|
| `modify` | Заменяемый фрагмент | Новый текст |
| `delete` | Удаляемый фрагмент | Пусто |
| `add` | Якорь: фрагмент, после которого вставить текст | Добавляемый текст |

Кроме того, у правки есть `section_ref`, `rationale`, `confidence_score`, статус (`pending`, `accepted`, `rejected`), автор и время решения, а также `edited_text` — редакция пользователя.

### Ревью

- **Решения по одной правке или пакетом** — `PATCH /suggestions`: принять, отклонить или вернуть в `pending` по списку идентификаторов или по фильтру (`pending`, `decided`, `all`). Статус документа при этом не меняется.
- **Сохранение сессии ревью** — `PUT /suggestions/review`: весь набор решений одним запросом. Принимаемая правка может нести `edited_text` — текст, исправленный пользователем; при экспорте он используется вместо текста модели. Запрос атомарно увеличивает `review_version`; клиент передаёт ожидаемую версию в `If-Match`, и если документ параллельно изменили, получает 412. С `finalize=true` и без оставшихся `pending` документ переходит в `ready`.
- **Отмена решения** — `POST /suggestions/{s}/reset` или статус `pending` в `PATCH`: правка снова ждёт решения, `edited_text` очищается. Отмена доступна и в `ready`: документ возвращается в `awaiting_approval`.
- **Сброс всего ревью** — `POST /editor/reset`: все решения и отметки флагов текущего анализа возвращаются в `pending`.
- **Флаги «проверьте вручную»** — `PATCH /flags/{f}`: отметить место просмотренным или снять отметку. На статус документа и экспорт не влияет.
- Каждое решение и отметка флага записываются в журнал аудита.

Экран редактора получает всё одним запросом `GET /editor`: метаданные документа, разобранный текст, текст оригинала, страницу правок, счётчики по статусам и права (`can_analyze`, `can_review`, `can_export`, `can_delete`, `sources_is_editable`), вычисленные из жизненного цикла. Режим отображения `view_mode` подсказывает клиенту, что показывать: `original` до анализа, `suggested` во время ревью, `clean` для готового документа.

### Применение правок и экспорт

Экспорт (`GET /documents/{d}/export`) доступен только для документа в статусе `ready` и только в исходном формате. Принятые правки текущего анализа читаются страницами и применяются к исходному файлу по порядку выдачи (`created_at`, `position`, `id`). Для каждой правки используется `edited_text`, если пользователь его задал, иначе текст модели.

Правки v2 применяются по своим границам (`start_offset`/`end_offset`), если текст файла под ними совпадает с `original_text`: так каждое из повторов фразы меняется в своём месте, а все такие правки собираются за один проход. Правки без границ (`legacy_llm`) и правки, чьи границы не совпали с файлом, применяются по правилам ниже.

Текстовые форматы (`.txt`, `.md`, `app/infrastructure/exporters/text_exporter.py`):

- `modify` и `delete` заменяют первое вхождение `original_text`;
- `add` вставляет новый абзац сразу после строки, в которой заканчивается якорь, с пустой строкой вокруг;
- если фрагмент или якорь не найден, правка не применяется: место за модель не угадывается.

`.docx` (`app/infrastructure/exporters/docx_exporter.py`):

- `modify` и `delete` ищут абзац, содержащий `original_text`, и переписывают его текст;
- `add` вставляет новый абзац после абзаца с якорем.

`.pdf` (`app/infrastructure/exporters/pdf_annotation_exporter.py`): текст файла не переписывается, правка ставится аннотацией рецензирования по сохранённой `geometry`. Файл дописывается инкрементальным сохранением, поэтому его начало побайтно совпадает с исходником.

- `modify` и `delete` зачёркивают старый текст (`/StrikeOut` с `QuadPoints` по прямоугольникам строк), в `/Contents` лежит новый текст или «Удалить»;
- `add` ставит знак вставки (`/Caret`) справа от символа перед точкой вставки, текст вставки лежит в `/Contents`;
- автор аннотаций (`/T`) задаётся `PDF_ANNOTATION_AUTHOR` (по умолчанию `SyncScribe`);
- у каждой аннотации есть поток внешнего вида (`/AP`), чтобы её рисовали и просмотрщики, которые не строят вид сами;
- правка на нескольких страницах даёт аннотацию на каждой странице, продолжения связаны с первой через `/IRT` и `/RT /Group`;
- правка без геометрии (сбой поиска при анализе) ставится заметкой `/Text` в левом верхнем углу первой страницы с текстом «было/стало», чтобы принятая правка не пропала из файла.

Клиент в режиме чистовика применяет правки в том же порядке и по тем же правилам, поэтому то, что пользователь видит на экране, совпадает с экспортом. Исключение — повторяющиеся фразы: пока клиент не перешёл на границы правок (SyncFront, F2/F8), он показывает вторую правку той же фразы как пересечение, а экспорт применяет её на своём месте. Исходный файл без правок отдаётся через `GET /documents/{d}/file` (для просмотра в браузере) и `GET /documents/{d}/download` (ссылка на скачивание из хранилища).

## Жизненный цикл документа

Все допустимые переходы и действия описаны в одном месте — `app/domain/lifecycle.py`. Сервисы, воркер и роутеры не держат собственных наборов статусов.

```
draft ──анализ──▶ in_progress ──есть правки──▶ awaiting_approval ──все решения приняты──▶ ready
  ▲                  │  └───────────нет правок──────────────────────────────────────────▶ │
  └──сбой или отмена─┘                                                                   │
awaiting_approval, ready ──повторный анализ──▶ draft ──▶ in_progress                      │
ready ──отмена решения или сброс ревью──▶ awaiting_approval ◀──────────────────────────────┘
```

| Действие | Когда разрешено |
|---|---|
| Запуск анализа | `draft`, `awaiting_approval`; из `ready` — только с `force=true`, потому что прежнее ревью будет сброшено |
| Изменение источников | Везде, кроме `in_progress`: воркер читает источники во время анализа |
| Ревью | `awaiting_approval` |
| Отмена решений | `awaiting_approval`, `ready` |
| Экспорт | `ready` |
| Удаление документа | Везде, кроме `in_progress` |

Задача анализа: `pending` (создана) → `dispatched` (в очереди) → `processing` (воркер начал) → `success`, `partial_success`, `failed` или `cancelled`. На документ допускается одна активная задача. Статус документа следует за его текущей задачей; завершение устаревшей задачи документ не трогает. Повторный запуск с тем же заголовком `Idempotency-Key` возвращает уже созданную задачу.

## Фоновый анализ

Анализ выполняет Celery-воркер (`app/workers/tasks/analysis_tasks.py`).

1. API создаёт задачу, переводит её в `dispatched` и ставит в очередь группу: по подзадаче на каждый источник и завершающую задачу после них. Если очередь недоступна, задача сразу становится `failed` с кодом `QUEUE_UNAVAILABLE`, документ возвращается в `draft`.
2. Первая подзадача переводит задачу в `processing`. Текст документа разбирается один раз и кэшируется в Redis на час.
3. Перед вызовом модели подзадача захватывает источник: ставит ему статус `processing`, срок аренды 10 минут и токен владельца. Это нужно, чтобы при повторной доставке задачи второй воркер не платил за второй запрос к модели, а воркер, у которого источник перехватили по истечении аренды, не смог записать устаревший результат. Проигравший ждёт и повторяет попытку каждые 30 секунд, до 20 раз.
4. Правки источника и отметка о его завершении пишутся в одной транзакции и только если задача ещё активна. Повторная доставка той же подзадачи не вызывает модель и не дублирует правки.
5. Завершающая задача подводит итог: все источники успешны — `success`, часть — `partial_success`, ни одного — `failed`. Уже завершённая (например, отменённая) задача не перезаписывается. После фиксации транзакции публикуется SSE-событие о смене статуса документа.

Коды ошибок источника: `LLM_INPUT_TOO_LARGE`, `LLM_UNAVAILABLE`, `LLM_INVALID_RESPONSE`, `DOCUMENT_PARSE_ERROR`, `GENERATION_ERROR`, `SOURCE_BUSY`. Задача хранит код и сообщение первой ошибки или сводку ошибок при частичном успехе.

## Архитектура

```
app/
├── api/            HTTP: роутеры FastAPI, схемы запросов и ответов, зависимости авторизации
├── domain/         сценарии, жизненные циклы, value objects, доменные события и исключения, порты
├── infrastructure/ адаптеры портов: PostgreSQL, S3-хранилище, Redis, очередь, LLM, SSE,
│                   парсеры и экспортёры документов, безопасность
├── workers/        Celery-задачи анализа и маппер ответа модели
└── core/           настройки, логирование, внедрение зависимостей, middleware
```

- Зависимости направлены внутрь: `domain` не импортирует FastAPI, SQLAlchemy, Redis и `infrastructure`. Внешние системы подключаются через порты в `app/domain/interfaces` (`IUnitOfWork`, репозитории, `FileStorage`, `AnalysisQueue`, `LLMClient`, `IEventPublisher` и другие).
- Сервисы работают с сущностями через протоколы (`DocumentProtocol`, `SuggestionProtocol`); ORM-модели остаются в инфраструктуре.
- Границы слоёв проверяются в CI скриптами `scripts/check_layer_imports.py` (запрещённые импорты) и `scripts/check_layer_contracts.py` (вызовы несуществующих методов портов и неизвестные аргументы).

## API

Полная спецификация — [`docs/openapi.json`](docs/openapi.json) (OpenAPI 3.1). На запущенном сервере она доступна по `/openapi.json`, интерактивная документация — по `/docs`.

Все эндпоинты, кроме `/health` и `/api/v1/system/capabilities`, находятся под `/api/v1` и требуют `Authorization: Bearer <access_token>`. Роль `admin` видит все проекты, `user` — только свои. Чужой проект отвечает 404, а не 403, чтобы не раскрывать его существование.

| Группа | Основные эндпоинты |
|---|---|
| Аутентификация | `POST /auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `GET /auth/me` |
| Проекты | `POST/GET /projects`, `GET/PATCH/DELETE /projects/{p}` (с `?include=documents&include=sources`) |
| Документы | `POST/GET /projects/{p}/documents`, `GET/DELETE …/{d}`, `…/{d}/content`, `…/{d}/file`, `…/{d}/download`, `…/{d}/export`, `POST …/{d}/sources`, `POST …/{d}/open` |
| Все документы пользователя | `POST/GET /documents` с фильтрами, поиском и сортировкой |
| Источники | `POST /projects/{p}/sources` (ссылка), `…/sources/note`, `…/sources/file`, `GET …/sources`, `GET …/{s}/content`, `GET …/{s}/file`, `DELETE …/{s}` |
| Анализ | `POST/GET/DELETE /projects/{p}/documents/{d}/analysis-jobs[/{j}]`, массовый запуск `POST /projects/{p}/documents/analysis-jobs/bulk` |
| Правки и ревью | `GET/PATCH …/{d}/suggestions`, `GET …/suggestions/{s}`, `PUT …/suggestions/review`, `POST …/suggestions/{s}/reset` |
| Редактор | `GET …/{d}/editor`, `POST …/{d}/editor/reset` |
| Флаги «проверьте вручную» | `GET …/{d}/flags`, `PATCH …/{d}/flags/{f}` |
| Главная | `GET /dashboard`, `GET /documents/attention`, `GET /documents/recent` |
| События | `GET /events/documents` — SSE со сменой статусов документов |
| Система | `GET /system/capabilities` (форматы, лимиты, правила для клиента), `GET /system/analysis-health` (готовность анализа, только `admin`), `GET /system/llm-health` (устарел, только `admin`), `GET /health` |

Соглашения:

- **Пагинация** — `limit` и `offset`; ответ `{"items": [...], "total", "limit", "offset"}`.
- **Ошибки** — `{"detail": "..."}`. 400 — неверный запрос; 401 — нет или истёк токен; 404 — ресурс не найден или чужой; 409 — действие недопустимо в текущем статусе, анализ уже идёт, правка уже обработана; 412 — устаревший `If-Match`; 413 — файл больше лимита; 415 — неподдерживаемый формат; 422 — ошибка валидации или документ не разбирается; 423 — источники заблокированы на время анализа; 429 — превышен лимит запросов или вход временно заблокирован; 502 — ошибка хранилища.
- **Загрузка файлов** — multipart; размер тела ограничен ещё до чтения, файл передаётся в хранилище потоком, исходное имя хранится в базе и отдаётся в `Content-Disposition`.
- **SSE** — событие `document_status_changed` с `{document_id, project_id, status, current_analysis_job_id}` получает только владелец проекта; `ping` каждые 25 секунд. События воркера доходят до API через Redis.

Перегенерировать спецификацию после изменения API:

```bash
python -c "import json; from app.main import app; print(json.dumps(app.openapi(), ensure_ascii=False, indent=2))" > docs/openapi.json
```

Для импорта приложения нужны переменные окружения из `.env`.

## База данных

PostgreSQL, миграции Alembic в `alembic/versions` (одна голова). Описание таблиц, связей, индексов и ограничений — [`docs/db/SCHEMA.md`](docs/db/SCHEMA.md), полный DDL — [`docs/db/schema.sql`](docs/db/schema.sql).

Основные сущности:

- `users` → `projects` → `documents` и `sources`; связь документа с источниками — `document_sources`;
- `analysis_jobs` — запуски анализа документа, `analysis_job_sources` — состояние обработки каждого источника в запуске;
- `suggestions` — правки, `suggestion_sources` — их связи с источниками истины, `audit_logs` — журнал решений и скачиваний;
- `document_opens` и `dashboard_snapshots` — данные для главной страницы.

Документ ссылается на свою текущую задачу (`current_analysis_job_id`); счётчики и экран редактора учитывают только правки текущей задачи, правки прежних запусков остаются в базе.

## Запуск

Нужны Docker и Docker Compose.

```bash
cp .env.example .env                 # заполните секреты; по умолчанию LLM_PROVIDER=stub
docker compose up --build
docker compose exec backend alembic upgrade head
curl http://localhost:8000/health
```

Compose поднимает `backend`, `worker`, `worker-analysis`, `postgres`, `redis` и `seaweedfs`. SeaweedFS работает одним процессом с S3-шлюзом на порту 8333; при старте он создаёт бакет и единственного пользователя с правами только на этот бакет из переменных `S3_*` (`docker/seaweedfs-start.sh`). Если обязательная переменная не задана, compose остановится с ошибкой.

Базовый compose не публикует порты PostgreSQL, Redis и SeaweedFS на хост. Для доступа с машины разработчика:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
```

Чтобы работать с настоящей моделью, задайте переменные из раздела [Подключение модели](#подключение-модели) и перезапустите `backend` и `worker`.

## Тесты и CI

```bash
ruff check app tests && ruff format --check app tests
python scripts/check_layer_imports.py app
python scripts/check_layer_contracts.py app
mypy app
pytest -m "not integration" tests --cov=app    # unit и контрактные, без внешних сервисов
pytest -m integration tests/integration        # нужны PostgreSQL, Redis и SeaweedFS
```

Unit- и контрактные тесты работают без внешних сервисов: SQLite в памяти, fakeredis, хранилище в памяти. Интеграционные тесты поднимают реальные PostgreSQL, Redis и SeaweedFS и проверяют сквозные HTTP-сценарии, гонки ревью и захвата источников, работу хранилища.

CI (`.github/workflows/ci.yml`) на каждый push и pull request:

- `lint-and-test`: ruff, проверки границ слоёв, mypy, unit- и контрактные тесты с порогом покрытия 70%;
- `check-migrations` — одна голова Alembic, `upgrade head` на чистой базе, сверка схемы с моделями (`alembic check`), откат до нуля и повторное применение;
- `integration-tests` — интеграционные тесты на PostgreSQL, Redis и SeaweedFS;
- `build-images` — сборка образов API и воркера.

## Безопасность

- Пароли хранятся в bcrypt; хеширование выполняется в отдельном потоке и не блокирует обработку запросов. При регистрации проверяется сложность пароля.
- Access-токен JWT с обязательным сроком жизни; refresh-токены хранятся в Redis и меняются при каждом обновлении, повторное использование старого токена отклоняется, выход отзывает токен.
- Вход блокируется после серии неудачных попыток по паре email и IP; на эндпоинты аутентификации действует ограничение частоты. Адрес клиента берётся из `X-Forwarded-For` только от доверенных прокси.
- Источники-ссылки защищены от SSRF (см. [Источники](#источники)).
- Бакет хранилища приватный, скачивание идёт по подписанной ссылке с ограниченным сроком. Приложение работает под пользователем хранилища с правами только на свой бакет.
- В промпте данные отделены от инструкции, ответ модели проверяется схемой и ручным ревью.
- CORS без `*`; логи структурированные, секреты из них вырезаются, текст документов и ответы модели в логи не пишутся.

## Ограничения

- Хранится только текущее состояние документа и результат последнего анализа, истории версий нет.
- Ролей внутри проекта нет: доступ есть у владельца и у глобального `admin`.
- В `.docx` анализируются и правятся только абзацы основного текста. Таблицы, колонтитулы и сноски не читаются.
- В `.docx` правка переписывает абзац целиком одним фрагментом текста с оформлением его первого фрагмента, поэтому смешанное форматирование внутри изменённого абзаца (жирный, курсив, ссылки) теряется. Стиль абзаца сохраняется.
- Правки применяются по первому вхождению фрагмента. Если одна и та же фраза встречается в документе несколько раз или две правки пересекаются, результат может отличаться от ожидаемого.
- В текстовых форматах после экспорта неразрывные пробелы заменены обычными — побочный эффект нормализации.
- Отделение данных от инструкции снижает риск prompt injection, но не исключает его.
- `robots.txt` источников-ссылок пока не соблюдается, а только логируется.
- Журнал аудита растёт без политики хранения.
